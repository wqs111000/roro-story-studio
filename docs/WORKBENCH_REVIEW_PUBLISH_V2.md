# Roro 绘本工作台审核与一键上架方案 v2

> 历史设计记录（2026-08-31），保留问题背景与实施方案，不作为当前操作手册。下文“必须先修正的问题”、默认 PIN、全页原图检查及实施顺序描述当时设计。当前采用开发模式免 PIN、联系表加标记页原图复核，详见 [制作管线](PRODUCTION_PIPELINE.md) 和 [当前质量规范](PICTURE_BOOK_WORKFLOW.md)。

更新日期：2026-08-31
状态：已实现并完成隔离端到端验收；正式候选等待家长在工作台决定

## 目标

将绘本制作流程收敛为：

1. Codex 完成故事、分镜、插图、音频与内部质量审核。
2. 内部审核未通过时由 Codex 自行返修，不要求家长参与中间 Gate。
3. 只有通过内部审核、资产范围明确的候选包进入网页工作台。
4. 家长在工作台选择“通过并上架”或“退回修改”。
5. “通过并上架”在一次受保护的服务端事务中持久化批准决定，并把准确候选版本发布到书架。

家长只保留最终决定权；自动检查、文件存在和 Codex 内部通过均不等同于家长批准。

## 当前实现必须先修正的问题

- 工作台从草稿 `story.json` 的旧 `status` 与 `parent_review.approved` 推断批准状态。草稿中出现新 v2 候选后，旧批准字段仍会让卡片错误显示“已批准”。
- 工作台按文件名统计全部 `page*.png`，v1 与 v2 同时存在时会显示“12/6 页图”，无法证明家长看到和批准的是哪六张。
- 页面图片通过文件名排序隐式选取，没有显式候选清单，也没有把批准决定绑定到内容哈希。
- 当前服务只有 GET/HEAD，且设置 `Access-Control-Allow-Origin: *`、监听局域网；直接增加无保护 POST 会让同一网络中的其他页面有机会触发写操作。
- 现有 `approved/<story-id>/` 是可变目录。直接覆盖会破坏旧批准证据，也无法安全回滚。

因此，按钮实现前必须先建立独立审核状态、候选清单、内容摘要、受保护写接口和不可变发布版本。

## 新工作流

```text
创作中
  ↓
Codex 内部审核
  ├─ 未通过 → 自动返修 → 再审核
  └─ 通过 → 生成候选清单与内容摘要
                    ↓
              等待家长审核
                ├─ 退回修改 → 保留意见与旧版本 → Codex 返修
                └─ 通过并上架 → 持久化决定 → 原子发布 → 书架立即显示
```

如果同一本已上架绘本产生新版本，书架继续播放旧版本，直到新版本再次通过家长审核。新审核不得使旧版暂时下架。

## 状态模型

| 状态 | 含义 | 工作台操作 |
|---|---|---|
| `authoring` | 正在制作或返修 | 不进入家长审核队列 |
| `ai_review_failed` | 内部检查发现阻断问题 | 显示为“制作中”，不可批准 |
| `ready_for_parent` | 内部审核通过，候选包已锁定 | 可“通过并上架”或“退回修改” |
| `changes_requested` | 家长已退回并留下意见 | 等待 Codex 返修，不影响旧书架版本 |
| `publishing` | 正在复制并校验发布包 | 按钮锁定，防止重复提交 |
| `published` | 当前候选已批准并成为书架版本 | 提供“在书架打开” |
| `publish_failed` | 批准已记录但发布事务失败 | 保留旧书架版本，可安全重试 |
| `stale` | 候选文件在审核后发生变化 | 原批准失效，必须重新内部审核和家长审核 |

状态由独立审核记录决定，不再从 `story.json.status` 推断。

## 候选包与审核记录

每本草稿新增：

```text
drafts/<story-id>/review/
  candidate-manifest.json
  ai-review.json
  parent-review.json
```

### `candidate-manifest.json`

明确列出本次要审核和发布的唯一资产，禁止通过通配符猜测版本：

```json
{
  "schema_version": 1,
  "story_id": "2026-08-30-sneezing-tiger",
  "candidate_revision": "roro-20260831-001",
  "assets": {
    "story": "story.json",
    "storyboard": "storyboard.json",
    "narration": "narration.json",
    "cover": "images/cover-v1.png",
    "pages": [
      "images/page-01-v2.png",
      "images/page-02-v2.png",
      "images/page-03-v2.png",
      "images/page-04-v2.png",
      "images/page-05-v2.png",
      "images/page-06-v2.png"
    ],
    "primary_audio": "audio/narration-higgs-lady.wav"
  },
  "asset_hashes": {},
  "package_digest": "sha256:..."
}
```

`package_digest` 根据规范化候选清单及每个文件 SHA-256 计算。页面、音频或文本任一文件改变，摘要必须改变，原审核状态自动变为 `stale`。

### `ai-review.json`

记录 Codex 内部审核结论，而非家长决定：

- 文本年龄适配、原创与安全边界。
- 角色图鉴版本、Roro 形态和故事内尺度锚点。
- 场景锚点、全画幅、无底栏、肢体和文字异常。
- 六页总览及逐页原尺寸检查。
- 音频存在、可播放、时长、异常静音与指定主音轨。
- 审核时间、候选摘要、问题和返修次数。

只有 `result: passed` 且记录的摘要等于当前 `package_digest`，故事才进入 `ready_for_parent`。

### `parent-review.json`

保存当前决定和完整历史：

```json
{
  "schema_version": 1,
  "current": {
    "decision": "approved",
    "scope": "complete_story_package",
    "candidate_revision": "roro-20260831-001",
    "package_digest": "sha256:...",
    "decided_at": "2026-08-31T12:00:00+08:00",
    "actor": "parent-workbench",
    "note": ""
  },
  "history": []
}
```

退回和重新批准均追加历史，不覆盖旧决定。

## 发布目录与无损更新

新发布结构采用不可变版本：

```text
approved/<story-id>/
  current.json
  releases/
    <candidate-revision>/
      story.json
      storyboard.json
      narration.json
      images/
      audio/
      approval.json
      package-manifest.json
```

- `releases/<revision>/` 一旦发布不再原地修改。
- `current.json` 只保存当前书架指向的版本和摘要。
- 服务端先在工作区临时目录复制允许清单中的资产，逐个校验哈希，再原子更新 `current.json`。
- 发布中途失败时删除临时包，不改变当前书架指针。
- 旧版本始终保留，可回滚且不会因新返修被覆盖。
- 书架接口同时兼容现有旧版平铺目录，迁移可以逐本进行。

## 写接口设计

| 方法与路径 | 用途 |
|---|---|
| `GET /api/studio/review-queue` | 返回真正等待家长决定的候选包 |
| `GET /api/studio/stories/<id>` | 返回候选清单、内部审核、当前决定和发布状态 |
| `POST /api/studio/stories/<id>/decision` | 写入“通过并上架”或“退回修改” |
| `GET /api/studio/stories/<id>/decision-history` | 查看历史决定和版本 |
| `GET /api/stories` | 继续返回当前已发布版本；发布后无需重启即可刷新 |

“通过并上架”的请求必须携带页面当前显示的 `candidate_revision`、`package_digest` 和一次性请求 ID。服务端执行：

1. 校验登录会话、同源请求和 CSRF Token。
2. 重新计算候选摘要；不一致则返回 `409 stale_candidate`。
3. 检查内部审核通过、所有必需资产完整且主音轨可播放。
4. 以故事 ID 加锁，防止双击或两个设备同时发布。
5. 写入家长批准记录。
6. 创建不可变发布版本并逐文件校验。
7. 原子更新当前书架指针。
8. 返回书架地址和发布版本。

同一个请求 ID 重试应返回同一结果，不生成重复版本。

- 桌面端维持三栏；中间画面是视觉焦点，右栏默认展示简明通过项，可展开技术详情。

- “通过并上架”使用实心森林绿；“退回修改”使用陶土红描边，不让两个按钮视觉权重相同。
- 每页缩略图显示已查看圆点，但不把“全部点开”作为强制批准条件。
- 音频播放器沿用现有样式，明确标出最终将发布的主音轨。

### 通过交互

点击“通过并上架”后显示单一确认弹层：

> 将批准并上架当前候选：6 页插图、完整文本和 Lady 音频。发布后书架立即更新，旧版本仍会保留。

弹层展示候选版本、更新时间和资源摘要，主按钮为“确认通过并上架”。成功后：

- 状态即时变为“已上架”。
- 显示轻量成功提示，不使用大面积庆祝动画。
- 提供“在书架打开”和“返回审核列表”。

### 退回交互

点击“退回修改”打开简洁抽屉，提供可多选的问题标签：

- 角色不一致
- 角色相对大小漂移
- 场景不连续
- 构图或底栏问题
- 文本需要修改
- 音频需要修改
- 其他

备注为可选；提交后故事进入 `changes_requested`，家长能看到意见已保存。退回不会删除草稿，也不会影响书架上的旧版本。

## 本地与局域网安全

工作台加入写能力后，不能继续让任意来源无认证写入：

- GET 静态资源可维持现状；所有写接口只接受同源请求，不返回 `Access-Control-Allow-Origin: *`。
- 首次在某个浏览器执行批准或退回时输入家长 PIN；会话 Cookie 使用 `HttpOnly`、`SameSite=Strict`，并设置合理有效期。
- 每次写请求校验 CSRF Token、`Origin`/`Host`、JSON Content-Type 和请求体大小。
- 服务端只接受严格故事 ID、候选清单中的相对路径和允许扩展名；继续阻止 `..`、绝对路径和软链接越界。
- 审核事件记录时间、来源设备的匿名会话 ID、候选摘要和结果，不记录照片内容或不必要的个人信息。

如果工作台只在本机使用，可提供“仅本机写入”模式；局域网浏览仍可只读。默认建议启用家长 PIN，以兼顾手机审核。

## 内部审核进入队列的最低门槛

- `story.json`、`storyboard.json`、`narration.json` Schema 通过。
- 候选清单恰好选择故事需要的页数，不混入旧版本和联系表。
- 每页图片尺寸、文件解码和哈希正常。
- 六页联系表和逐页原图已经目视检查。
- 同一故事角色相对尺度、角色图鉴身份与 Roro 形态连续。
- 重复场景的固定布局、地标、门窗、家具、持续道具和摄影轴线连续。
- 母版全画幅，无底栏、文字占位、边框或水印。
- 主音频存在、可播放，时长合理，无异常长静音。
- 内部审核记录绑定当前候选摘要。

任何阻断项未通过时，“通过并上架”按钮不出现；页面只显示“Codex 正在返修”。

## 测试与验收

### 服务端

- 状态转换合法性及非法跳转拒绝。
- 候选摘要变化后旧批准自动失效。
- v1/v2 并存时只展示清单指定的六页，不再出现“12/6”。
- 重复点击、重复请求和并发设备不会重复发布。
- 发布失败保持旧书架版本可用。
- 不覆盖旧 `releases/`，可切换回上一版。
- 路径穿越、错误 Origin、缺失 CSRF、无 PIN 会话均被拒绝。

### UI

- 1440 px、1024 px、768 px 和 390 px 宽度下无溢出或按钮遮挡。
- 键盘可完成翻页、播放、退回和批准；焦点清楚。
- 通过、退回、失效、发布中和发布失败状态都有明确反馈。
- 书架在批准成功后刷新即可看到新版本并播放指定音频。

## 建议实施顺序

1. **数据与安全基础**：候选清单、摘要、审核记录、状态机、PIN/CSRF 和测试。
2. **无损发布器**：不可变 release、原子 current 指针、旧目录兼容和回滚测试。
3. **工作台 UI**：审核队列、三栏审片台、通过/退回弹层、移动端布局。
4. **端到端验证**：用一份复制的测试故事验证通过、退回、失效、重试和书架播放。
5. **正式启用**：备份现有审核记录，迁移当前故事；确认后再移除“只读工作台”提示。

建议不要把“写按钮”和“复制到 approved”分成两个家长步骤。UI 中保持一次“通过并上架”，服务端内部仍按“记录决定 → 校验 → 发布 → 更新书架指针”的安全事务执行。
